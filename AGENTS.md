# Guía del proyecto (para cualquier agente: Claude Code, Gemini Antigravity, etc.)

Antes de escribir o modificar código, lee **`docs/ARCHITECTURE.md`** — arquitectura, patrones (AppContext híbrido, autorización por refugio con `x-user-id`, cola offline con backoff), modelo de datos, rutas API y esquemas de trabajo del proyecto. Está pensada para entender el repo rápido sin explorarlo entero ni quemar tokens.

Reglas base innegociables:
- **Estas instrucciones (AGENTS + `SKILL.md` + `ARCHITECTURE.md`) son INNEGOCIABLES.** Léelas al empezar CADA tarea y cúmplelas. Lo que el dueño indique como regla se acata siempre, aunque no esté escrito aún. **Si surge una convención NUEVA (de estilo, UX, arquitectura, etc.), PREGÚNTALE al dueño antes de incluirla** en el skill/AGENTS; una vez confirmada, codifícala aquí para que toda IA (Claude, Gemini Antigravity, etc.) la cumpla.
- **Sistema de UI "todo pill" (reformat innegociable).** En cualquier formulario/modal, TODOS los controles comparten UNA sola altura y radio pill vía las clases `.censo-form` (registro) o `.pill-form` (reutilizable: envuelve la sección con `pill-form`). Usa SIEMPRE los componentes reformateados —`StyledSelect`, `DatePicker`, `SearchableSelect`, `SearchableSingleSelect`— y **NUNCA** `<select>` ni `<input type="date">` nativos. **Ningún control ni botón puede quedar con altura distinta** (inputs, selects, date, y botones `btn-submit`/`btn-secondary`/`btn-back` van todos al mismo alto `--ctl-h`). Búsquedas insensibles a acentos con `normalizeText`. **Verifica visualmente** (mismo alto, esquinas pill, sin saltos de tamaño de letra) antes de dar por hecho un cambio de UI.
- **Botoneras AGRUPADAS (regla de tema visual innegociable).** Los botones que forman un conjunto de acciones NO van sueltos: van **agrupados** como una unidad visual coherente. Dos patrones reutilizables en `globals.css`:
  - **Grupo segmentado** (`.btn-seg-group`): envuelve varios `.toolbar-btn` en un contenedor pill único con divisores; el texto colapsa a solo-ícono en pantallas angostas (`.btn-txt-collapsible`, ≤560px). Úsalo para toolbars (exportar, imprimir, etc.).
  - **Grupo de íconos con tinte por acción** (`.row-actions` + `.btn-ver` cuadrado redondeado + variantes `--room` verde / `--view` azul / `--edit` ámbar): íconos de acción de fila, cada acción con su color semántico. Úsalo para acciones por registro.
  Al crear una botonera nueva, usa uno de estos patrones (o extiéndelos); nunca dejes botones de un mismo set desalineados o con estilos dispares. **Verifícalo visualmente.**
- `npx tsc --noEmit` debe quedar limpio antes de cada commit.
- **Equivalencia de registros (una sola fuente, innegociable).** Cuando un mismo tipo de registro pueda crearse por VARIAS vías de UI (p. ej. censo individual y la carga familiar del Paso 5), TODAS deben armar el objeto con la MISMA función (`buildRegistroData` en `CensoTab`) y pasar por la misma cola/`/api/register`, para que el registro quede **idéntico** sin importar por dónde se creó. **No dupliques el armado del registro** ni metas variantes por vía.
- **Deja el puerto 3000 libre para el dueño.** Si levantas un servidor para tus PRUEBAS (dev o build de producción), usa OTRO puerto (p. ej. 3001 dev / 3100 prod). Nunca ocupes el 3000.
- **El Service Worker y el aviso de "actualizar" son SOLO de PRODUCCIÓN** (`next start`). `next dev` NO registra el SW (guard `NODE_ENV !== "production"` en `page.tsx`), así que en dev NO hay aviso y bumpear el `BUILD_TS` no hace nada. **OJO:** un SW viejo de un build de producción anterior **persiste por-origen** y sigue sirviendo CACHE VIEJA aunque cambies a `next dev` en el mismo puerto → el dueño ve UI vieja. **Para que el dueño VEA los cambios de UI con su aviso de "actualizar", corre un build de PRODUCCIÓN en 3100 y bumpea el `BUILD_TS`:**
  1. `npm run build`  2. `node scripts/update-sw-version.mjs --dev` (BUILD_TS único; va DESPUÉS del build, porque el `prebuild` pone el commit SHA que NO cambia entre iteraciones sin commit)  3. reinicia el server prod-3100. El dueño recarga → el SW detecta la versión nueva → sale el aviso → acepta → recarga con lo nuevo.
  En deploy real (Vercel) el `prebuild` hornea el commit SHA solo. Si iteras en `next dev` (HMR, más rápido) no hay SW/aviso; si ves cache vieja, hay un SW viejo → desregístralo (DevTools → Application → Service Workers → Unregister) una vez.
- **Nada de hardcode.** No incrustes valores fijos en el código (refugios, nombres, capacidades, listas, credenciales, cualquier cosa que deba venir de la BD / config / estado / `.env`). Si te topas con hardcode existente, **adviértelo y propón la solución** (parametrizarlo, moverlo a BD/config/entorno) en vez de dejarlo pasar.

Ejecuta `node scripts/send-push-email.mjs "<asunto>" <cuerpo.html>`; usa Resend con la API key en `.claude/resend.key` (**gitignored, NUNCA commitear** ni pegar en código). - **Antes de iniciar un cambio:** consulta `docs/ARCHITECTURE.md` para partir del estado real del proyecto (no de suposiciones).

- **Cambios en la BD:** todo cambio de esquema (`prisma/schema.prisma`) → actualizar el schema + `npx prisma generate` + **entregar al dueño el SQL de migración idempotente** para ejecutarlo **manualmente en Supabase** (NO se corre `prisma migrate` ni `db push` automático contra producción). Idempotente = re-ejecutable sin romper: `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `DROP ... IF EXISTS`, `INSERT ... ON CONFLICT DO NOTHING`, `UPDATE ... WHERE`.
